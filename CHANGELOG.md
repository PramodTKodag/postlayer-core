# Changelog

All notable changes are recorded here. Format based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versions follow [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Added
- `docs/USAGE.md`: every function with who can call it, `cast` examples for publishing, reading, liking, tipping and owner administration, the events, the errors, and a note on calling from another contract. The examples were run against a local chain. README links it and shows a short example.
- `make test-docs` (part of `make ci`) compares the compiled contract's ABI with `docs/USAGE.md` and the README, so a function, event or error that is added, renamed or re-typed without updating the guide fails CI. It also checks every `"name(types)"` or `"name(types)(returns)"` signature the commands pass to `cast` (input types, return types with struct fields, `indexed` fields), and the events and errors tables list each field's and argument's type.
- Open-source community files: `CODE_OF_CONDUCT.md` (Contributor Covenant 2.1, conduct reports through GitHub's private reporting), `SUPPORT.md`, `GOVERNANCE.md`, `CITATION.cff`, `docs/USED_BY.md`, bug and feature issue forms (blank issues off, with security and Discussions links), and README badges plus a license-and-credit section.
- Dependabot weekly updates for GitHub Actions, npm and the Solidity submodules, and a pinned OpenSSF Scorecard workflow that publishes its result and uploads it to code scanning.
- An `SPDX-FileCopyrightText` line in every contract and script source, so the copyright notice travels with the verified source of a deployment. Comments only: the compiled bytecode is unchanged.
- The deploy script itself now refuses to broadcast unless the chain id equals `EXPECTED_CHAIN_ID`, the factory has the pinned code, and `OWNER` has code on that chain (or, declared an EOA with `OWNER_IS_EOA=true`, has no contract code). `release.sh deploy` sets `EXPECTED_CHAIN_ID` from `chains.json` and refuses a chain that is not in `CHAINS`. Before, only the optional preflight enforced these checks. The checks live in `script/DeploymentGuards.sol`, shared with the preflight.
- `make require-release-env` refuses `FOUNDRY_*` and `DAPP_*` settings in `.env` (any letter case): they change the compiled bytecode (and so the addresses) while the manifest records the `foundry.toml` settings.
- A contract-wallet `OWNER` must now also match `OWNER_CODEHASH` on every target chain, checked by `release-preflight` and by the deploy script itself. Before, any code at `OWNER` passed, so a different contract that claimed the address on another chain first was accepted. A missing pin, a malformed pin (not 32-byte hex) and `OWNER_IS_EOA=true` together with a pin are each refused with their own error, and `release.sh` asks for the pin up front and shows the owner mode or pin on the deploy confirmation. `checkChain` and `broadcastDeploy` take the extra `ownerCodehash` argument. The pin does not prove who controls the wallet; see `docs/AUDIT.md`.
- `.github/FUNDING.yml` enables the repository Sponsor button for the maintainer's GitHub Sponsors profile. Changes to it need the maintainer's review (`CODEOWNERS`), because it decides where donations go.

### Changed
- The repository is renamed from `postlayer-core` to `postlayer` (GitHub redirects the old URL). Links, the npm package name, the Compose project name and the tooling image tag (`postlayer-tools:local`) follow; rebuild the image with `make image`. The README banner shows the new name. Contract names, bytecode and deployed addresses are unchanged.
- An owner declared an EOA (`OWNER_IS_EOA=true`) is refused when it has contract code (`OwnerIsEoaHasCode`); the code of an EIP-7702 delegated account (`0xef0100` plus the delegate address) does not count, because that account is still controlled by its key. Before, the flag skipped every owner check, so a contract wallet declared an EOA by mistake (for example from a reused testnet `.env`) passed preflight and deploy.
- The `release` container builds into its own `/tmp` output and forge cache, ignores the workspace's Python bytecode (`script/__pycache__`), and has its own compiler and RPC-cache volumes, so every `make release-*` command compiles from scratch and the other tooling's build output, forge cache and compiler binaries cannot change the bytecode a release deploys. Before, it reused the workspace `out/` and `cache/` and shared the compiler volume with `tools`, so tampered build output would have been deployed while the manifest still recorded `gitTreeClean: true`. The workspace itself (sources, `lib/`, `foundry.toml`, `.git`) is still shared read-write with `tools`; release from a fresh clone (`docs/AUDIT.md`). Recovery of an interrupted `release-deploy` is to run it again (existing contracts are skipped); `forge script --resume` no longer works because the cache is discarded. `make test-release-isolation` (part of `make ci`, runs in the tools container) checks the setup.
- `make upgrade-reference` exports each dependency at the commit the release tag pinned instead of linking the current `lib/`, so a dependency bump cannot hide a storage-layout change from the upgrade validator. It fails with the dependency and commit it cannot find. `make test-release-tools` tests the export on a scratch repository.

### Fixed
- Docs corrected against the code: README, `SECURITY.md` and `docs/ARCHITECTURE.md` no longer say real-chain deployment has not happened (`testnet-0.1.0` is on Ethereum Sepolia); the architecture doc no longer says the timelock exists or that the interfaces are frozen; `docs/CONVENTIONS.md` examples use names that exist in the repo; the changelog is split into `Unreleased` and `testnet-0.1.0` instead of repeating headings; `CONTRIBUTING.md` has the real clone command.
- `release.sh preflight`, `deploy`, `check` and `fork-test` hide any `scheme://...` text in forge's output (`script/hide_urls.py`, placeholder `<url hidden>`), including the normalized form forge prints (lowercased host, default port dropped), which an exact-string match misses. A bare host is not recognised and `forge verify-contract` is not filtered. Output is streamed, forge's exit status is kept (128 plus the signal number when it is killed), SIGINT and SIGTERM are passed on, and the filter always waits for forge. The manifest writer uses the same rule for `cast` errors. `release.sh deploy` and `verify` no longer print `cast`'s error text when the RPC does not answer `chain-id`, and a chain id listed twice in `CHAINS` is rejected by `release.sh` and the manifest writer.
- `make test-fork` takes the RPC URL from `FORK_RPC_URL` instead of `FORK_URL=...`, so it is no longer on a command line, and runs at `-vv` with URLs hidden.
- The local deploy test no longer depends on `OWNER_IS_EOA` being unset: forge fills an unset variable from a developer's own `.env`.

## [testnet-0.1.0] - 2026-10-09

First testnet release, tagged `testnet-0.1.0`. Not audited.

### Added
- `release-preflight` now requires `OWNER` to have code on every target chain unless `OWNER_IS_EOA=true` is set, so a contract-wallet owner that does not exist on one chain cannot become the owner of that chain's proxy. `checkChain` takes `owner` and `ownerIsEoa`.
- Documented that tips go to the publishing address and do not follow ownership changes (deploy with the final owner from day one).
- `docs/AUDIT.md`: scope, trust model, tested invariants, known limitations and static-analysis triage for reviewers.
- Testnet release tooling: env-driven chain configuration, a read-only preflight, a `release` service that is the only one mounting keystores and receiving `.env` as environment variables (`.env` still sits in the workspace mount, so do not run untrusted code in the other containers while it holds real RPC keys), per-chain deploy with confirmation, Sourcify and Etherscan verification, a post-deploy check, a release manifest writer, a fork deploy test (`make test-fork-release`), and the runbook in `docs/DEVELOPMENT.md`. `make up` also exercises preflight, check and manifest against the local chains.
- Tipping module and token allowlist: `tipPost(postId, token, amount)` pays the post's author directly in the native coin (zero address) or an owner-approved ERC-20, and the owner sets or removes approved tokens with a per-token minimum above zero (`setTokenAllowed`, `setTokenDisallowed`, `tipConfig`). Rules: the author cannot tip their own post, hidden posts take no tips, the amount must meet the minimum, `msg.value` must match the native amount and be zero for ERC-20, and a rejected payout reverts the whole tip. No fee and no held balances. Covered by unit, fuzz and stateful invariant tests, plus an upgrade test that keeps the allowlist across an upgrade.
- Reactions module: free `likePost`/`unlikePost` with `likeCount` and `hasLiked` reads, in its own ERC-7201 storage. The author cannot like their own post, each address likes a post once, hidden posts take no new likes (unliking still works). Covered by unit, fuzz and stateful invariant tests, plus an upgrade test that keeps likes across an upgrade.
- Same-address deployment script for `SoloPostLayer` through the deterministic CREATE2 factory, a deployment check script, and `make deploy-check` for the two local chains. `make up` now deploys to both chains and checks the addresses match.
- Post registry (publish, update with version history, hide/unhide) and UUPS `SoloPostLayer`, with `renounceOwnership` disabled. `Post` fields are ordered so an update never writes the first storage slot.
- Upgrade-safety check (`make test-upgrades`) with the OpenZeppelin validator pinned to 1.46.0 in `package.json` and `package-lock.json`.
- Dockerized development environment: pinned tooling image (Foundry, Node.js, Slither, Aderyn), two local anvil chains, Makefile, CI workflow.
- Project documentation: README, architecture, development, conventions, contributing and security policy.

### Changed
- `make test-upgrades` now validates `SoloPostLayer` against a build of the released tag (`testnet-0.1.0`), so storage-layout regressions against the released version fail. New `make upgrade-reference` builds that baseline; CI fetches tags for it.
- Release manifests (`deployments/`) are no longer committed. The repo ships the deploy tooling only; every integrator deploys and records their own instance.
- Chain id replaces chain name as the identifier everywhere in the release tooling; names are display-only. `chains.json` is keyed by chain id (`"11155111"`, `"84532"`), each entry's `chainId` must equal its key, and an optional `name` (1-40 letters, digits, spaces, `_`, `.`, `-`) appears in messages and the manifest. `CHAINS` in `.env` lists ids, `make release-deploy` and `make release-verify` take `CHAIN=<chain id>`, the deploy confirmation is the chain id, the private RPC override is `CHAIN_<id>_RPC_URL`, the forge scripts and the fork test read `CHAIN_<id>_RPC_URL` and `CHAIN_<id>_ID`, the manifest `chains` object and `script/local-chains.json` are keyed by id, and ids are validated as digits without a leading zero, at most 18. A `.env` that still lists chain names fails with `chain '<name>' is not a chain id; use e.g. 11155111`; update `CHAINS` and rename any `<NAME>_RPC_URL` to `CHAIN_<id>_RPC_URL`.
- Non-secret chain data moved from `.env` into a committed `chains.json` (chain id, explorer URL and a default public RPC URL per chain), read through `script/chain_config.py`. `.env` now holds only `CHAINS`, the owner, salt, deployer and keystore settings, and an optional `CHAIN_<id>_RPC_URL` override for a private RPC; adding a chain is one JSON entry. `chains.json` rejects an `rpcUrl` with credentials, a query string, a fragment or `;` params, an `explorerUrl` with credentials, a query string or a fragment, and any whitespace or control character in a URL. Real releases refuse `CHAINS_FILE`: `chain_config.py` (so `release.sh` and the manifest writer) fails unless the local flow opts in with `LOCAL_CHAINS_OK=1`, and the `make release-*` guard fails early if `.env` has any line setting either variable. `chains.json` also rejects repeated keys and an unreadable or non-UTF-8 file with a clean error, and `chains.json` and `script/chain_config.py` now have a CODEOWNERS entry. `make test-fork-release` goes through the new `release.sh fork-test`, and the local `make up` flow reads `script/local-chains.json`.
- `script/CheckDeployment.s.sol`: `run` now takes RPC URL environment-variable names and chain ids (`run(string[],uint256[])`) instead of URLs, reverts with `LengthMismatch` when the lists differ and with `WrongChainId` when an RPC reports another chain, and exposes the per-chain checks as `checkChain`. `make release-check` therefore checks chain identity, and `make release-verify` refuses to run when the RPC reports another chain id.
- The release manifest writer now fails unless the original deploy's broadcast file exists, holds successful transactions and created the predicted implementation and proxy; it writes the file atomically and warns on a dirty git tree.
- `PreflightDeployment.predict()` logs one machine-readable `PREDICTED implementation=... proxy=...` line, the only thing the release helpers parse.

### Fixed
- `release.sh preflight` and `check` replace every configured RPC URL (from `chains.json` or a `CHAIN_<id>_RPC_URL` override) with `<rpc url hidden>` in forge's output, on success and on failure, and keep forge's exit status; forge's output now appears once it finishes. `release.sh deploy` and `verify` no longer print `cast`'s error text when the RPC does not answer `chain-id`, and a chain id listed twice in `CHAINS` is rejected by `release.sh` and the manifest writer.
- `release.sh deploy` now gives `forge script` the RPC URL through `FOUNDRY_ETH_RPC_URL`. `forge script` ignores `ETH_RPC_URL`, so the deploy simulated on an empty local chain and failed with `FactoryNotDeployed`. The URL still stays out of argv.
- `release.sh deploy` now runs `forge script` with `--skip-simulation --slow`. Forge's local simulation under-priced contract creation on Ethereum Sepolia, so the gas limit was too low and both deploy transactions reverted on-chain (the factory's CREATE2 ran out of gas). Each transaction's gas is now estimated by the chain, and the proxy is sent after the implementation is confirmed.
